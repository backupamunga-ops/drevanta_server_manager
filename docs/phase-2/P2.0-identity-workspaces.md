# P2.0 RFC — Identity, personas, and workspaces (finalized)

**Status:** Finalized design — targets v0.5.0
**Decided:** 2026-11-13 (product decision by the owner; supersedes the
v1.0 conservative interpretation in the PRD)
**Requirements source:** [PHASE2_PRD.md](PHASE2_PRD.md) v1.1 §4–§7, §21,
§27 (OD-001 decided)
**Design rules for all UI:** [../DESIGN_PRINCIPLES.md](../DESIGN_PRINCIPLES.md)

This document is the single source of truth for the P2.0 identity
model. It fixes what the PRD left as "proposed default" where the
product owner has now decided, and states the implementation shape for
Drevanta (`drevantad`, SQLite, embedded SvelteKit console).

## 1. The decided model in one paragraph

Four personas map onto four workspace types — `server`,
`hosting_org`, `website`, `developer_project` — with one login and
many memberships per user. **Switching workspaces never grants
privileges**: every authorization decision is re-made per request
against memberships and roles stored server-side. Persona switching
and customer management are different things: a reseller/agency opens
and manages authorized customer websites **from within its Hosting
workspace** (agency management mode) and reaches a Website Owner
context only via separate membership or an audited support grant.

## 2. Personas and workspace types

| Persona | Workspace type | Scope | Phase 2 status |
|---|---|---|---|
| Server Administrator | `server` | Linux administration, server ownership | Fully functional |
| Reseller / Hosting Provider / Agency | `hosting_org` (+ `business_type`) | Hosting organizations and customers | Foundation: org, team, customer directory, delegated site access |
| Website Owner | `website` | Website-level controls | Foundation: workspace + membership only; no fake UI |
| Developer | `developer_project` | Application-level controls | Foundation: workspace + membership only; no fake UI |

`hosting_org.business_type ∈ {reseller, hosting_provider, agency}` is
an attribute, not a separate workspace type — one interface, one
authorization model, extensible later with billing, quotas and
white-labeling.

The hierarchy Server Administrator → Hosting → Website/Developer
describes **management relationships** (organizational ownership,
delegated tasks), never permission inheritance.

## 3. Switching matrix (decided)

| Current persona | Server workspace | Hosting workspace | Website workspace | Developer workspace |
|---|---|---|---|---|
| Server Administrator | Own authorized servers | Yes, authorized | Own/assigned | Own/assigned |
| Reseller / Agency | No* | Yes | Via assigned sites (agency management mode) | Via assigned projects |
| Website Owner | No* | No* | Yes | If assigned |
| Developer | No* | No* | If assigned | Yes |

\* Unless the same user independently receives membership in that
workspace. No persona automatically grants another persona's
permissions.

## 4. Agency management mode vs Website Owner mode

The same `website` workspace can be entered in two modes, and the mode
is derived server-side from the actor's membership — never selected by
the browser:

- **Agency management mode** (actor holds a `hosting_org` role and the
  site is an assigned customer resource): the console shows the
  delegated hosting-management surface for that site (hosting
  allocation view in Phase 2; service settings when Phase 3 ships).
  The actor stays in their Hosting workspace context; navigation back
  to the customer directory is always present. Customer-private data
  (files, credentials) stays out of this mode.
- **Website Owner mode** (actor holds a `website` membership): the
  owner view — their site, its domains/SSL/files/backups as those
  features ship. No agency-wide customer list, no server
  administration.

Both modes are audited (`workspace_entered` with mode + actor +
workspace). The Acme Hosting example: an agency managing 50 websites
opens any of them from its customer directory without 50 website-owner
accounts; owners of those sites see only their own site.

## 5. P2.0 ground rules (decided, binding for implementation)

1. A Server Administrator can create and manage hosting organizations
   on their server, but accessing customer-private data requires an
   appropriate grant or audited support access.
2. A Reseller can manage their own hosting customers and assigned
   websites, but cannot manage the underlying Linux server.
3. A Website Owner controls only their assigned websites.
4. A Developer controls only their assigned applications or projects.
5. A user can hold multiple roles across different workspaces without
   needing separate accounts.
6. The platform must never equate workspace switching with privilege
   escalation.

## 6. Roles and permissions

- Role templates per workspace type follow PRD §6.1 (server:
  `owner`/`administrator`/`operator`/`viewer`; hosting_org:
  `owner`/`manager`/`staff`/`viewer`; website:
  `owner`/`manager`/`viewer`; developer_project:
  `owner`/`maintainer`/`viewer`), stored as
  `roles` + `role_permissions` rows, not hardcoded checks.
- Permission keys follow PRD §6.2's namespace, implemented as a Go
  registry (`internal/workspaces/permissions.go`) seeded into SQLite so
  the API can check `role_permissions` authoritatively. In Phase 2 only
  `workspace.*` and `system.*` keys are operational; `hosting.*`,
  `website.*`, `developer.*` keys exist as foundation rows and gate
  nothing until their milestones ship (PRD §6.2 caveat).
- **Phase 1 scope mapping (migration):** the existing scopes
  (`ScopeFull`, `ScopeOnboarding`, `ScopeRecovery`) become role
  permissions inside the owner's auto-created `server` workspace:
  `ScopeFull` ≙ server `owner`, `ScopeOnboarding` ≙ the pre-claim
  onboarding grant, `ScopeRecovery` ≙ the password-recovery grant. The
  migration (PRD §21.3: migrate Phase 1 tables, never duplicate) wraps
  every existing user/session in the first `server` workspace
  atomically; sessions keep working across the upgrade.
- Authorization algorithm per request: PRD §6.3 — resolve workspace
  from the route, verify membership or active support grant, resolve
  the resource's authoritative workspace relation, check the
  permission, record the decision. The browser-selected workspace ID is
  never trusted as proof of access (PRD §5.3).

## 7. Data model (implementation shape for 0.5.0)

Normalized per PRD §21.2 with the migration caveats (§21.3): indexes,
FK enforcement, active-invitation uniqueness, hierarchy cycle
prevention, audit append-only. Additions decided here:

- `workspaces.business_type TEXT NULL CHECK (business_type IN
  ('reseller','hosting_provider','agency'))` — set only when
  `type = 'hosting_org'`.
- `workspace_memberships.state ∈ {active, revoked, expired}` +
  `expires_at`; revocation invalidates cached permissions promptly
  (PRD §21.3).
- `sessions.active_workspace_id` is advisory UI state only (which
  context the shell renders); it contributes nothing to authorization.
- `support_grants` (OD-002, still open): time-limited, reason-coded,
  customer-approval-first; modeled but dormant until the policy is
  decided.

## 8. API and UI shape

- New endpoints (workspace-scoped): `GET /api/v1/workspaces` (the
  caller's memberships), `POST /api/v1/workspaces/{id}/enter` (switch;
  re-authorized server-side), `POST /api/v1/workspaces` (server admin
  creates a hosting org — foundation), `POST
  /api/v1/workspaces/{id}/members` + invitations (foundation). Exact
  routes and payload shapes are settled in the 0.5.0 implementation
  against PRD §20.
- The workspace selector lives in the shared header (PRD §7.1) and
  lists only workspaces with a valid membership or active grant,
  grouped by persona, with role + status. Foundation workspaces appear
  only when a membership exists — the shell never shows placeholder
  buttons for features that do not exist (DESIGN_PRINCIPLES.md §7).
- Switching clears workspace-scoped state, refetches permissions and
  navigation, and shows the unmistakable active-workspace banner on
  every mutation screen (PRD §5.3).
- Audit: `workspace_entered`, `workspace_switched`,
  `membership_changed`, `hosting_org_created`, support-grant events —
  actor, effective workspace, target, decision (PRD §5.5).

## 9. What is explicitly NOT in P2.0

No billing, no customer hosting provisioning, no website runtime
controls, no Git deployment, no Docker, no mail hosting (PRD §0
deferred list). Hosting/website/developer workspaces are foundation
rows with honest navigation states; Phase 3/4 gates decide when they
become functional (PRD §32).
