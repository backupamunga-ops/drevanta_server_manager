# P2.1 — Observability & resource signals: implementation RFC

Status: **decided** (implementation-ready) · Milestone: **0.5.1** ·
Date: 2026-11-13 · Predecessor: [P2.0-identity-workspaces.md](P2.0-identity-workspaces.md) (shipped in 0.5.0)

Scope from the Phase 2 plan: *server overview; metric history with
bounded retention + downsampling; process list; service health;
alerts; first preflight API*. Drevanta-specific shape: extend
`internal/metrics/` with **no new daemons**; new `metric_samples` /
`health_alerts` tables with retention budgets; **read-only** role
access verified against the P2.0 registry.

## D-01: one in-process sampler, no helper, no systemd timers

A goroutine inside `drevantad` collects a `metrics.Snapshot` every
**15 s** (configurable for tests) and writes one raw row. Rationale:
the collector already reads /proc on demand; a loop around it costs
nothing extra to operate, keeps the single-binary deployment story,
and 15 s is 4× finer than any chart the UI draws. The sampler owns
exactly one lifecycle: start after migrations, stop on shutdown; it
must never panic the daemon (recover + log + continue).

## D-02: storage shape and the 512 MB budget

Migration 0006 adds:

- `metric_samples` — raw 15 s rows: `taken_at` (RFC3339Nano UTC),
  `cpu_percent`, `load1/5/15`, `mem_used/available/total_bytes`,
  `swap_used/total_bytes`, `disks` (JSON array of per-mount
  {path, total, available, used_percent}).
- `metric_samples_5m` — downsampled rows: `bucket_start`, the same
  numeric columns as **avg**, plus `cpu_max`, `mem_max`,
  `disk_worst_max` (worst-mounted-disk %), `samples_count`.
- `health_alerts` — deduplicated alert rows (D-04).

Retention (the budget decision): **raw rows live 24 h; everything
older is folded into 5-minute aggregates which live 14 days**. Worst
case ≈ 5,760 raw rows + ≈ 4,032 aggregate rows on disk — low single
digit megabytes even before WAL checkpointing, safe on the 512 MB-class
target. The retention pass runs inside the sampler loop every
downsampler tick (default 15 min) and runs in one transaction per
bucket range so a crash cannot half-fold a bucket. `PRAGMA`-free,
pure SQL.

APIs never mix tiers: the history endpoint returns raw rows for the
last 24 h and aggregates beyond that, stitched at a bucket boundary
and labelled in the response (`resolution: "raw" | "5m"` per point).

## D-03: history & overview read model

- `GET /api/v1/server/metrics/history?window=1h|24h|7d|14d` →
  `{points: [{t, cpu_avg, cpu_max, mem_avg, mem_max, disk_worst}],
  resolution per point}`. `cpu_max`/`mem_max` are 0 for raw rows
  (the raw value is the point), averages carry the live value.
- `GET /api/v1/server/overview` → the one call the console renders
  on load: live snapshot (on-demand collect, as today), last-24h
  sparkline data (≤ 288 points), active alerts, systemd summary
  (running/failed/enabled counts), worst disk, uptime.
- Both require the **server workspace context** and
  `system.overview.read` / `system.metrics.read` respectively (P2.0
  registry; read-only).

## D-04: alerts are evaluated, deduplicated and anti-flapped

The sampler evaluates four conditions on every tick, using the
registry namespaces only (no new permission keys — alerts surface
under `system.overview.read`):

| kind | warn | crit |
|---|---|---|
| disk | any mount ≥ 80 % | any mount ≥ 90 % |
| memory | available ≤ 10 % | available ≤ 5 % |
| load | load5 > 2 × cores for 3 consecutive ticks | — |
| swap | swap_used ≥ 80 % of swap_total | ≥ 90 % |

`health_alerts` rows are keyed by `(kind, subject)` — one open row
per condition (subject = mount path, `memory`, `load`, `swap`);
escalation warn→crit updates severity in place with `last_seen_at`.
**Anti-flap**: a condition must hold 2 consecutive ticks to open and
clear 2 consecutive ticks to resolve. Open/close transitions write
`alert_opened` / `alert_resolved` audit events (actor `drevantad`) so
the P2.0 audit log tells the whole story. The API
`GET /api/v1/server/alerts` returns open alerts first, then resolved
within the last 24 h. Alert rules are constants in this milestone;
tuning knobs are explicitly deferred to P2.5.

## D-05: process list is computed, never stored

`GET /api/v1/server/processes` reads /proc on request and returns the
top 50 by CPU% measured over a **500 ms in-request delta window**
(per-process jiffies now vs. +500 ms), with pid, ppid, user, state,
RSS, CPU%, and a truncated cmdline. Rationale: process lists are
point-in-time; persisting them violates the budget for near-zero
value. Latency is ~0.5 s per call, acceptable for a manual-refresh
view. Permission `system.processes.read`, server context.

## D-06: service health via two systemctl calls, no dbus

`GET /api/v1/server/services` parses
`systemctl list-units --type=service --all --no-legend` (load, active,
sub, description) joined with
`systemctl list-unit-files --type=service --no-legend` (enablement
state). Two subprocess calls, no dbus dependency, no root needed.
`failed`/`maintenance` units sort first. Permission
`system.services.read`, server context. **No actions**: start/stop/
restart arrive with the P2.2 privileged helper — this milestone is
deliberately read-only end to end.

## D-07: the first preflight API

`GET /api/v1/server/preflight?kind=<name>` returns
`{ok, checks: [{name, ok, value, threshold, message}]}`. 0.5.1 ships
`kind=package_upgrade`: disk headroom ≥ 15 % on `/` and `/boot` (when
present), memory available ≥ 300 MB, load5 < cores, no active
`crit` alert. It is the foundation P2.4's upgrade workflow and P2.5's
cross-module preflights build on — one stable envelope, check list
grows per kind. Read-only; permission `system.overview.read`. Unknown
kinds answer 400 with the known list.

## D-08: UI surfaces honestly, read-only

The console (server workspace context only, as decided in P2.0)
gains an overview plus two new sections — **Processes** and
**Services** — reached from a tab strip on the shell. The sections
are deep-linkable routes (`/` overview, `/processes`, `/services`)
rendered with the same shell; no per-chart routes beyond that:

- Overview: existing snapshot cards + 24 h sparkline (history API),
  an alerts strip (open alerts; resolved collapsed), systemd failed
  counter, worst-disk card.
- Processes: table sorted by CPU% (manual refresh + 10 s auto while
  visible; refresh is honest about the 500 ms measurement window).
- Services: full unit table with enablement; failed rows highlighted;
  an explicit note that actions arrive in P2.2 (no fake buttons —
  DESIGN_PRINCIPLES.md).

Alert states and empty states are first-class: "no active alerts" is
a real state, not a suppressed block.

## D-09: non-goals

No retention config UI, no per-unit thresholds, no notification
channels (email/webhook), no historical process/service snapshots,
no write actions on services. Each is explicitly re-decidable at
P2.5/0.6.0 without touching this milestone's schema.

## Test matrix (must be green before release)

- Bucket math: 15 s → 5 m folding (4×20 samples), window stitching,
  retention cuts both tables (clock-injected).
- Alert lifecycle: open at threshold, escalate, anti-flap resolution,
  dedup by subject, audit events written.
- API: history/overview/processes/services/alerts/preflight status
  codes for anonymous / onboarding-scope / full-server-context /
  org-context (`403 workspace_mismatch`) callers; preflight unknown
  kind 400.
- Read-only proof: services/processes endpoints perform no mutations
  (source inspection + no helper binary shipped).
